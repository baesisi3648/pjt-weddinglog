# 01 — Product Requirements Document (PRD)

> 결혼 준비 과정의 기록이 그대로 앨범이 되는 서비스

---

## 프로젝트 개요

**서비스명**: WeddingLog (웨딩로그)

**한 줄 요약**: 결혼을 준비하는 커플이 공유 캘린더에 준비 과정과 스냅샷을 기록하고, 그 기록이 자동으로 결혼앨범(책)이 되는 웹 서비스

**서비스 구조**: 
- **본체**: 결혼 준비 과정 기록 서비스 (캘린더, 체크리스트, 타임라인)
- **부가 기능**: 기록된 콘텐츠를 앨범으로 주문하기

**타겟 사용자**: 결혼 준비 중인 2030 커플 (특히 스냅스, 아이폰 스냅 같은 빠른 사진 서비스를 사용하는 세대)

**개발 조직**: 스위트북 바이브코딩 풀스택 개발자 과제 (신입 1인)

**개발 기간**: 7일 (2026.4.23 ~ 2026.4.29)

---

## 배경: 실제 경험에서 출발

이 서비스는 **작년 결혼을 직접 경험한 개발자의 페인포인트**에서 출발했습니다.

> "양가 인사를 다니며 부모님께 앨범을 보여주고 싶었는데, 본식앨범이 나올 때까지 3개월을 기다려야 했다. 그 사이 스냅스(아이폰 스냅)는 이미 다음날 배송이 왔고, 우리는 스프레드시트로 준비 일정을 따로 관리했다. '기록이 바로 책이 될 수는 없을까?'라는 생각에서 이 서비스를 기획했다."

### 시장 현황
- **본식앨범**: 100~300만원, 3~6개월 대기 (낙후된 기술)
- **아이폰스냅 등 빠른 포토서비스**: 다음날 수령 (선진 기술)
- **현재 결혼 준비 현황**: DIY 스프레드시트 + 카카오톡 + 인스타그램 혼재

이 괴리를 WeddingLog가 해소하려고 합니다.

## 문제 정의: 3가지 페인포인트

### 1. 뭘 언제 해야 하는지 몰라서 흩어진다
**증상**: 결혼 준비 항목이 수십 개인데, 누가 언제 뭘 챙길지 가이드가 없음
- 예식장, 스드메, 예물·예단, 청첩장, 식전영상 등 준비 과정이 체계화되지 않음
- 부부가 각자 메모, 블로그, 카톡 등 다른 곳에서 정보 검색
- "우린 이걸 잘했나?" 싶어도 되짚어보기 어려움

**영향**: 준비 누락, 중복, 스트레스

### 2. 기록이 흩어져서 나중에 모아보기 힘들다
**증상**: 결혼 전후 사진이 여러 곳에 산재
- 웨딩촬영 사진 → 스튜디오 USB
- 스냅스 사진 → 배송 수령
- 신혼여행 사진 → 스마트폰 갤러리
- 준비 과정 스냅샷 → 카카오톡, 인스타그램

**영향**: 나중에 앨범 만들려고 할 때 사진을 한데 모으는 데만 며칠 소요

### 3. 앨범을 제때 못 받는다 (가장 치명적)
**증상**: 본식앨범은 빨라도 3개월, 느리면 6개월 소요
- **타이밍 불일치**: 양가 인사는 결혼 직후(D+3~D+14) → 앨범이 있어야 할 시점
- **기술 역행**: 아이폰스냅은 다음날 받는데 앨범은 반년 기다림
- **비용 부담**: 100~300만원 가격대로 인한 결정 부담

**영향**: "앨범 없이 부모님께 인사하기" → 효도의 완성도 저하, 실감 부족

## 솔루션

### 세 가지 기둥

#### 1. AI가 자동으로 준비 체크리스트를 만든다
- 사용자가 결혼 예정일만 입력
- OpenAI API가 D-180 ~ D+14 범위에서 15개 사전 일정 생성 (또는 템플릿)
- 매 단계마다 "언제, 뭘 해야 하나" 제시
- 사용자는 자유롭게 수정/추가/삭제 가능

#### 2. 한 곳에서 모든 기록을 시각화한다
- **공유 캘린더**: 부부가 함께 보는 월간 캘린더
- **일정 상세**: 각 일정에 메모 + 사진 업로드 (일정당 최대 10장)
- **타임라인 뷰**: 카테고리별 챕터로 자동 묶음 → "책의 미리보기"
- **AI 캡션**: 사진 업로드 시 카테고리 맥락의 감성적 캡션 자동 제안

#### 3. 기록에서 1~2주 내 앨범을 주문한다
- 신혼여행 끝나면 "앨범 만들기" 클릭
- 앨범 구성(판형, 표지, 수량) 선택 → 주문 생성
- 스위트북 파트너십으로 빠른 인쇄·배송
- **목표**: D+14 이내 앨범 수령 (부모님 방문 시 들려줄 수 있는 타이밍)

## 구현 스코프: Lv1 ~ Lv3 정의

**전략**: 기획은 Lv3까지 완성, 구현은 Lv1부터 완성도 중심으로 진행

### Lv1: 서비스 핵심 (MVP)
**목표**: 결혼 준비 기록 앱이 완전히 동작

필수 기능:
- 커플 프로필 (신랑·신부 이름, 결혼 예정일)
- AI 웨딩 체크리스트 자동 생성 (OpenAI 또는 템플릿)
- 공유 캘린더 (월간 뷰, 일정 CRUD)
- 일정별 사진 업로드 (최대 10장/일정, 5MB/장)
- AI 캡션 생성 (3개 옵션, 사용자 선택 또는 수정)
- 타임라인 뷰 (카테고리별 챕터 정렬, 사진 그리드 + 캡션)
- 더미 데이터 (샘플 커플 1쌍, 사전 등록 일정 10~15건, 사진 포함)

**완료 조건**: 
- docker-compose up으로 전체 서비스 기동 가능
- 로그인 없이 샘플 커플 데이터로 즉시 서비스 체험 가능
- 캘린더 → 일정 추가 → 사진 업로드 → AI 캡션 → 타임라인 뷰 전체 플로우 동작

**평가 포인트**: 서비스 플로우가 완성되는가

### Lv2: 자체 주문 기능
**목표**: 사용자가 기록을 "앨범으로 만들어달라"고 주문 가능

필수 기능:
- 주문 생성 (챕터 선택, 판형 선택[정사각형/A4], 표지 선택[하드/소프트], 수량[1~10권])
- 배송 정보 입력 (수령인, 연락처, 주소)
- 주문 상태 관리 (pending → processing → completed)
- 주문 목록 조회 및 상세 조회
- 주문 상태 변경 버튼 (시뮬레이션용)

**미구현 (의도적 포기)**:
- 실제 결제 처리 (Toss, Stripe 등)
- 실제 배송 추적
- 회원 인증 (로그인/회원가입)
- 실제 책 제작

**완료 조건**:
- 타임라인 뷰에서 "앨범 주문하기" 진입
- 주문 생성 → 상태 변경 → 주문 관리 페이지에서 조회 가능
- Lv1의 모든 기능 유지

**평가 포인트**: 비즈니스 로직이 작동하는가

### Lv3: 주문 데이터 익스포트
**목표**: 주문 1건의 모든 데이터를 구조화해 파트너(스위트북)에게 넘길 수 있는 형태로 출력

필수 기능:
- ZIP 다운로드 (주문 ID 기준)
- ZIP 내 구조:
  ```
  order_20260423_001.zip
  ├── order.json              # 주문 메타데이터
  ├── chapters/
  │   ├── 01_wedding_photo/
  │   │   ├── photo_001.jpg
  │   │   ├── photo_002.jpg
  │   │   └── ...
  │   ├── 02_preparation/
  │   └── ...
  └── captions.json           # 사진별 캡션 매핑
  ```

**미구현 (의도적 포기)**:
- 출력용 PDF 생성 (인쇄사 담당)
- 라벨, 바코드 생성

**완료 조건**:
- 주문 관리 페이지에서 "데이터 다운로드" 버튼 동작
- ZIP 파일이 올바른 구조로 생성
- order.json, captions.json 형식 검증 완료
- 실제 이미지 파일 포함 검증

**평가 포인트**: 데이터 모델링과 직렬화 능력

## 성공 지표

| 지표 | 기준 | 우선순위 |
|------|------|---------|
| **Lv1 완성도** | 캘린더 → 사진 업로드 → AI 캡션 → 타임라인까지 완벽 동작 | 필수 |
| **Docker 실행 가능** | docker-compose up 1회로 전체 서비스 기동 (로그인 X) | 필수 |

| **README 완성** | 심사자가 README만 보고 실행 가능할 정도로 상세 | 필수 |
| **AI 폴백** | OpenAI API 키 없어도 템플릿으로 체크리스트/캡션 반환 | 필수 |
| **Lv2 완성도** | 주문 생성 ~ 상태 관리까지 완벽 동작 | 권장 |
| **Lv3 완성도** | ZIP 다운로드 및 구조화 완벽 동작 | 도전 |
| **설계 의도 전달** | 면접에서 기획 배경과 기술 선택 설득 가능 | 필수 |

## 서술형 문항 준비 방향

### 문항 1: 서비스 기획 의도와 과정
**핵심**: 작년 결혼 경험 → 실제 페인포인트 → 솔루션

- 양가 인사 때 앨범이 없었던 아쉬움
- 본식앨범 3~6개월 vs 스냅스 다음날의 괴리
- "기록이 그대로 책이 된다"는 아이디어의 간단함과 강력함

### 문항 2: 바이브코딩(과제) 수행 과정
**핵심**: Claude Code/Cursor 등 AI 도구를 어떻게 활용했나

- 어떤 프롬프트를 주었는지 (기획서 기반 아키텍처 설계)
- 어떤 코드를 받았는지 (FastAPI 라우팅, React 컴포넌트)
- 실패한 부분은 어떻게 해결했는지

### 문항 3: 과제에서 내린 가장 중요한 판단
**핵심**: 기술/스코프 선택에서의 의사결정

- **스택 선택**: FastAPI(자산) + React(생산성) + SQLite(배포 간편) + Tailwind(스타일링 속도)
- **AI 기능 범위**: OpenAI API 폴백(심사자 편의) vs 구현 비용
- **Lv 선택**: Lv1 완성도 vs Lv3 도전 사이의 균형

### 문항 4: AI 도구 사용 중 겪은 실패 또는 문제
**핵심**: 솔직한 경험과 문제 해결 과정

- "Claude Code가 이렇게 생성했는데 동작하지 않아서 이렇게 수정했다"
- "OpenAI API 비용 우려로 템플릿 폴백을 결정했다"
- 예상과 달리 작동하는 부분, 추가로 보완한 부분
